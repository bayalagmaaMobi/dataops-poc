The Problem

Why does this exist?

Data teams have been working without the discipline that software engineers take for granted.

✗ Before DataOps

The old way — chaotic

  • ❌Someone edits a SQL query directly in production
  • ❌No record of what changed, who changed it, or why
  • ❌A broken formula produces wrong revenue numbers
  • ❌The business finds out from a wrong report
  • ❌You can't roll back — the old version is gone
  • ❌Nobody reviewed the change before it went live
✓ With DataOps

The new way — controlled

  • ✅Every change lives in Git — full history forever
  • ✅You know who changed what, when, and why
  • ✅Automated tests catch broken logic before merge
  • ✅The business is protected — bad code can't reach prod
  • ✅Roll back any change in 30 seconds
  • ✅Every PR has a mandatory human review + checklist
5 Pillars

How the system works

Click each pillar to understand it deeply — including real scenarios.

🗂️

1. Git — Version Control

Every file tracked. Full history. Roll back anytime.

Every SQL model, config file, and seed data CSV is stored in Git. This gives you a complete timeline of every change ever made — who did it, when, and what the message said.

Real scenario
A revenue report shows wrong numbers on Tuesday. You run git log and see that on Sunday someone changed the revenue calculation. You revert the commit in 30 seconds. Crisis over.
🌿

2. Branching — Protect main

main = production. All changes go through a branch + PR.

main is the protected production branch. Nobody — not even the repo owner — can push directly to it. Every change must go through a branch and a pull request.

Branch naming:

🟢 feature/ — new models, new data sources
🔵 fix/ — wrong calculations, bad data
🟡 chore/ — config updates, dependencies
📄 docs/ — documentation only
🚨 hotfix/ — urgent production fixes (still needs review!)

Real scenario
You need to add a churn rate model. You create feature/churn-rate-model, build it there safely — main stays working the whole time.
📋

3. PR Template — Structured review

Every PR has a mandatory checklist for author and reviewer.

When you open a PR on GitHub, a template automatically fills the description. Both sides must engage with it seriously.

Author fills in: what the PR does, what changed, how they tested it.

Reviewer ticks off:

  • SQL is readable and follows team style
  • Primary keys have not_null + unique tests
  • No hardcoded dates or credentials
  • schema.yml is updated for new columns
  • CI is passing before approving
Why it matters
Without a template, reviewers just glance at the diff and click approve. The template forces both sides to think carefully about the change.
⚙️

4. CI Pipeline — Auto quality gate

GitHub runs dbt seed → compile → run → test on every PR automatically.

The moment you open a PR, GitHub Actions spins up a clean server and runs the full dbt pipeline. If anything fails, the merge button stays blocked.

DataOps CI / Run dbt checks
✅ dbt seed — loaded 3 CSV files
✅ dbt compile — all SQL is valid
✅ dbt run — 5 models built
✅ dbt test — 22 tests passed
Real scenario
Someone writes a SQL join that creates duplicate rows. The unique test on customer_id fails. PR is blocked. Bug never reaches production.
🔍

5. Data Quality Tests — schema.yml

Every column in every model has rules. Violations = CI fails.

All tests are defined in schema.yml and run automatically on every PR.

Three types of tests:

not_null Column must never be empty

unique No duplicate values allowed

accepted_values Only specific values are valid

Example
plan column only accepts 'pro' or 'free'. If someone enters 'Premium', the test fails immediately.
👥

CODEOWNERS — Auto assign reviewers

GitHub automatically assigns the right reviewer based on what files changed.

The .github/CODEOWNERS file maps file paths to GitHub users. When a PR touches those files, the right person is automatically requested as a reviewer.

Current setup:

/models/ → @bayalagmaaMobi (data engineer reviews SQL changes)

/.github/ → @bayalagmaaMobi (lead reviews CI/config changes)

/seeds/ → @bayalagmaaMobi (anyone can review seed data)

In a real team
Different people own different files. The data engineer owns models, the team lead owns CI config, junior analysts own seed data. Reviews go to the right person automatically.

Data Models

How the data flows

Raw CSV → cleaned views → business tables. Three layers, each with a clear purpose.

SEEDS

Raw Data — CSV files loaded into the database

Fake sample data representing what real operational data looks like. Used to make CI work without needing a real database connection.

customers.csv

8 customers with name, email, country, signup date, plan (pro/free)

orders.csv

Orders with amount, status (completed / refunded / cancelled)

events.csv

User activity events — login, logout, purchase

↓
STAGING

Cleaned Views — standardized, typed, renamed

Takes raw seed data and makes it usable: lowercases emails, casts dates, derives calculated flags. Materialized as views (no storage cost, always fresh).

stg_customers

Adds is_paid boolean flag based on plan. Lowercases email.

stg_orders

Derives revenue — only counts completed orders, zero for refunded/cancelled.

stg_events

Cleans event types, ensures consistent formatting across event records.

↓
MARTS

Business Tables — answers real questions

Joins and aggregates staging models into tables the business actually uses for reporting. Materialized as tables (stored, fast to query).

mart_monthly_revenue

One row per month. Total revenue, completed orders, refunds, cancellations. Powers trend charts.

mart_customer_summary

One row per customer. Total orders, total spent, first/last order date. Powers customer reports.


Data Quality Tests

Every column has a rule. Breaking it blocks the merge.

Model Column Tests What it catches
stg_customers customer_id not_nullunique Duplicate or missing customers
stg_customers plan accepted_values Typos like "Pro", "premium", "PAID"
stg_orders order_id not_nullunique Duplicate orders, missing IDs
stg_orders status accepted_values Invalid statuses like "pending" or "DONE"
stg_events event_type accepted_values Unknown event types entering the pipeline
mart_monthly_revenue month not_nullunique Duplicate months in the revenue rollup

Real Scenarios

Every situation you might face

Click each scenario to see exactly what to do.

✏️
I need to change a SQL model
Normal everyday change — new logic, new column, refactor
▶
# 1. Always start from an updated main git checkout main git pull # 2. Create a branch with a clear name git checkout -b feature/add-churn-model # 3. Edit the SQL file in models/ # 4. Test locally first dbt run && dbt test # 5. Commit with a descriptive message git add . git commit -m "feat: add customer churn rate model" # 6. Push and open a PR on GitHub git push origin feature/add-churn-model

Then open the PR on GitHub → fill in the template → wait for CI → get 1 approval → merge.

❌
CI failed on my PR — what do I do?
Red X on the PR, merge is blocked
▶

1. Click the red ✗ → "Details" to see which step failed and the exact error.

2. Fix the issue in your code locally. Run dbt test yourself to confirm it's fixed.

dbt run && dbt test # All 22 tests passed? Good. git add . git commit -m "fix: resolve failing unique test on customer_id" git push origin feature/your-branch # CI reruns automatically on the new commit

Common failures: duplicate rows (unique test fails), wrong column values (accepted_values fails), syntax error (compile step fails).

🚨
I need to fix something urgently in production
A hotfix — something is wrong right now
▶
git checkout main git pull git checkout -b hotfix/fix-revenue-calculation # Make the fix git commit -am "hotfix: correct revenue calculation for refunded orders" git push origin hotfix/fix-revenue-calculation

⚠️ Even hotfixes go through a PR. Branch protection applies to everyone. This is intentional — a panicked direct push is how you make a bad situation worse.

⏪
A bad change got merged — how do I roll back?
Something wrong is now on main
▶
git checkout main git pull # Find the bad commit hash git log --oneline -10 # Revert it (creates a new commit that undoes it) git revert abc1234 # Open as a PR — revert also needs review git checkout -b fix/revert-bad-change git push origin fix/revert-bad-change

Use git revert not git reset --hard. Revert adds a new commit (safe, auditable). Reset rewrites history (dangerous on shared branches).

➕
I want to add a completely new model
New data source, new business question
▶

You need to do two things: create the SQL file AND add it to schema.yml with tests.

# 1. Create the model file # models/marts/mart_churn_rate.sql # 2. Add it to schema.yml with column tests # models/schema.yml - name: mart_churn_rate description: "Monthly churn rate calculation" columns: - name: month tests: [not_null, unique] - name: churn_rate tests: [not_null] # 3. Test locally dbt run --select mart_churn_rate dbt test --select mart_churn_rate

A model without tests in schema.yml is incomplete. CI will still pass but you lose the quality safety net.

📊
I need to update seed data (CSV files)
Adding new customers, new orders, fixing test data
▶

Seed files are versioned just like SQL. Edit the CSV on a branch, PR it in.

git checkout -b chore/update-seed-data # Edit seeds/customers.csv or seeds/orders.csv # Test that the new data passes all tests dbt seed dbt run && dbt test git commit -am "chore: add 5 new test customers to seed data" git push origin chore/update-seed-data

Make sure new rows don't break accepted_values or unique tests — e.g. a new customer with plan = "enterprise" will fail the test.

Speech Guide

What to say in your presentation

A ready-to-use script for each section of your talk.

Opening · ~1 minute

Start with the problem they recognize

"Right now, when someone on the data team changes a SQL query, a report formula, or a data file — what happens? Nothing is recorded. No one reviews it. If it breaks, we find out when the business gets a wrong number. And we have no way to know what changed or go back. This is exactly how software teams worked 20 years ago — before they developed a better way."
💡 Pause after "wrong number" — let it land before continuing.
What is DataOps · ~1 minute

Explain the concept in one sentence

"DataOps applies the same discipline that software engineers use to data work. Every change lives in version control. Every change goes through a review. Automated tests run before anything touches production. This project is a proof of concept showing exactly how that works — with tools that are free and run entirely on a laptop."
Live Demo · ~3-4 minutes

Walk them through the repo on screen

"Let me show you the repo. [Show GitHub] Every file you see — the SQL, the config, the test data — is tracked in Git. Full history, every change, every author. [Open a model file] This is a SQL model. Notice every column is documented and tested. [Open schema.yml] These are the rules — if any data violates them, CI fails and the merge is blocked. [Show the CI run] This is what happens automatically the moment someone opens a pull request. 30 seconds — GitHub runs the full pipeline. [Show the blocked merge] And this is the key moment. CI passed. But there's no approval yet. The system physically cannot merge. No human override exists."
💡 Show PR #1 — it was merged after CI passed. Show the branch protection settings page to prove the rules are enforced.
Business Value · ~1 minute

Connect it to what they care about

"When a report shows wrong revenue numbers, we will know within minutes exactly what changed, who changed it, and we can roll it back in seconds. When someone wants to add a new data source, it goes through review before it affects any report. When a new team member joins, they can read the full history of every decision ever made. This is how you build trust in your data — not with hope, but with process."
Closing · ~30 seconds

Simple, confident finish

"This runs entirely with free tools — Git, GitHub, dbt, and DuckDB. No servers, no infrastructure cost to get started. The process is the product. The discipline is the value."
💡 Stop there. Don't add "any questions?" immediately — hold the silence for 2 seconds first. It lands better.
